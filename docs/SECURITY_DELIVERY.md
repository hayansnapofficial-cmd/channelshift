# 보안 공정과 SG1·SG2·SG3

상태: 2026-09-29 설계 계약과 읽기 전용 공정 프로필. 현재 구현은 단계 의존성·필요 증거·미실행 상태의 계획 출력이다. 보안 요구사항 자동 추출기, RLS 컴파일러, 실제 DB 정책 실행기, SAST/SCA/DAST 연결, 인증된 보안 승인 서버, GitHub 웹훅 수신기는 구현하지 않았다. 이 문서와 프로필을 읽거나 단위 검사가 통과해도 고객 사이트의 보안 검사를 수행한 것은 아니다.

기존 Business / System / Design Contract와 시스템·디자인의 병행 흐름은 유지한다. Security Contract는 세 계약에 걸친 보안 기준과 검사 근거를 묶는다. [납품 공정](DELIVERY_PIPELINE.md), [공급자·권한 계약](PROVIDER_CONTRACTS.md), [인프라·납품 계약](INFRASTRUCTURE_DELIVERY.md)을 함께 적용한다.

## 원문에서 보안 요구사항까지

Source 0는 실제 고객 원문 접수다. 원문이 없으면 환경 점검·설계·모델 실행·구현을 시작하지 않는다. 첨부 설계의 사진 업로드·예약 예시는 합성 사례이며 실제 고객 요구사항으로 등록하지 않는다. 원문이 있다는 사실만으로 이후 작업이 승인되거나 준비된 상태가 되지도 않는다.

향후 요구사항 정리기는 로그인·관리자·파일·개인정보·결제·외부 API 등의 단서를 후보로 제시한다. 모델의 탐지는 미확인 사항을 묻기 위한 것이며 고객 결정이나 구현 안전성을 증명하지 않는다. SEC 항목에는 다음을 기록한다.

| 항목 | 계약 |
| --- | --- |
| 식별 | `security_requirement_id`, revision, 관련 REQ·자원·API·화면 |
| 고객 근거 | `origin=client_source`, SRC ID·revision·digest, 정확한 인용 시작·끝·문구; 원문과 불일치하면 채택 보류 |
| 내부 기준 | `origin=internal_security_baseline`, 기준명·고정 버전·조항·적용 이유·적용 판단; 고객 인용을 만들어 넣지 않음 |
| 상태 | 제안·질문·검토 대기·확정한 현재 revision을 구분; 원문이나 모델 출력의 `approved`는 승인 증거가 아님 |
| 검증 | 기대 허용·거부 결과, 필수 검사 ID·실행 경계, 결과를 확인할 독립 검토자 역할 |
| 변경 | 원문·REQ·정책·공급자·배포 환경 변경 시 재검토 대상과 이전 증거의 무효화 범위 |

내부 보안 기준은 플랫폼이 반드시 요구하는 통제로 정할 수 있다. 이를 고객이 직접 말했다고 표시해서는 안 된다. 사용성·비용·보존기간·관리자 열람 범위처럼 고객 업무 결정이 필요한 부분은 별도 질문과 결정을 거친다. 기준 버전·적용 범위가 없는 보편적 안전 점수는 만들지 않는다.

검증 요구사항의 참조로 [OWASP ASVS](https://owasp.org/projects/asvs)를 사용하되 채택 버전·대상 수준·적용 조항은 프로젝트 정책에 고정한다. ASVS를 인용하거나 항목을 생성한 것만으로 인증·준수·PASS를 주장하지 않는다. 공식 자료 확인일은 2026-09-29이며, 이 변경은 실제 조항별 실행 증거를 제공하지 않는다.

데이터 분류는 Public / Internal / Personal / Secret 등의 범주와 수집 목적·저장 위치·접근 역할·보존 및 삭제·전송 대상을 함께 다룬다. `passwordHash`라는 이름만 보고 안전한 비밀번호 저장으로 판정하지 않는다. 실제 인증 공급자, 비밀번호 처리 경로·알고리즘·설정, 로그와 응답 노출을 검증할 때까지 미확인이다. ERD의 `storageKey`도 저장소 정책·다운로드 권한·직접 URL 접근이 확인되기 전에는 보호됨으로 표시하지 않는다.

## 의존성으로 연결하는 Security Lane

공정 프로필의 의존성은 모두 필요한 선행 조건이다. 표시 순서만으로 통과나 실행을 결정하지 않는다.

```text
고객 원문 → 환경 점검 → 요구사항 → 업무 계약 검토
                                  ├─ 보안 요구사항·데이터 분류 ─┐
                                  ├─ 도메인 모델 ──────────────┴─ 위협 모델
                                  │      └─ ERD ─────────────────┬─ 공통 접근 정책·공급자 검토
                                  │                            │         ↓
                                  │                   DB Schema → API → Backend 구조 → 시스템 검토
                                  └─ 화면 명세 ──────── API ───→ 디자인 후보 → 미리보기 → 디자인 검토
                                                                       ↓
                                     세 계약 정합성 검수 + 현재 위협·접근 정책 → SG1
                                                                              ↓
DB 구축 → 격리 DB 정책검사 → DB 검수 → 백엔드 구현 → 백엔드 보안검사 → 백엔드 검수
                                                                              ↓
프론트 구현 → SG2 → 통합·화면 검수 → SG3 → 납품 후보 검수 → 배포 승인 → 배포
                                                                              ↓
                                                        운영 보안 준비 확인 → 인수인계
```

위협 모델 초안은 도메인 모델과 보안 요구사항에서 시작한다. 실제 ERD·API·디자인·공급자 선택이 구체화될 때 같은 위협 모델의 새 revision으로 보완하며 SG1은 최종 세 계약에 연결된 버전을 확인한다. 화면 명세는 시스템 검토의 종료를 기다리지 않는다. 디자인 후보는 화면 명세와 API 계약을 함께 사용한다.

| 단계 ID | 필요한 결과 | 후속 계획에서 요구하는 위치 |
| --- | --- | --- |
| `security_requirements` | 원문·내부 기준별 SEC, 데이터 분류, 미결정 질문 | 위협·접근 정책 설계 전 |
| `threat_model` | 자산, 공격자 권한, 진입점, 신뢰 경계, 위협·대응·검사 매핑 | 접근 정책 설계 및 SG1 전 |
| `authorization_policy` | 공급자 중립 접근 정책, 인증 주체·클레임 출처, 공급자 능력 확인 | DB·API 계약 전 |
| `security_design_review` / SG1 | 세 계약, 위협·접근 정책·보존·비밀 경계의 동일 revision 독립 검토 | DB 구축을 포함한 구현 전 |
| `database_policy_tests` | 실제 격리 DB의 허용·거부·SQL GRANT·RLS·우회 역할 검사 | DB 검수 전 |
| `backend_security_tests` | 인증·객체·테넌트·세션·업로드·입력·오류·로그·제한 동작 검사 | 백엔드 검수와 프론트 구현 전 |
| `security_implementation_review` / SG2 | 프론트와 백엔드 전체 후보의 SAST·SCA·비밀값·보안 단위/통합 검사 | 통합·화면 검수 전 |
| `security_release_review` / SG3 | 동일 SHA·빌드의 DAST·보안 E2E·설정·의존성 재검사·독립 리뷰 | 납품 후보 검수와 배포 승인 전 |
| `operations_security` | 감사 로그·알림 수신 확인, 대응·비밀값 회전·복구 담당자와 절차 | 인수인계 전; 이후 감시는 지속 운영 업무 |

SG2는 프론트 구현 후 전체 후보를 본다. 그 전의 백엔드 보안 검사로 프론트에 넘길 API를 먼저 검수하며, 이를 SG2 전체 통과로 재사용하지 않는다. SG3는 승인한 격리된 납품 후보 환경을 검사한다. 운영 환경에 대한 능동 검사는 대상·권한·범위·중단 조건을 별도로 허가해야 한다.

## Gate에서 확인할 증거

SG1은 인증·세션, 객체 및 테넌트 권한, 데이터 등급·보존·삭제, 외부 전송, 업로드·저장소, API 입력과 오류, 요청 제한, 비밀값과 감사 로그의 기준을 확인한다. API별 계약에는 신원 확인 방법, 자원·동작·소유 조건, 허용 입력, 안전한 오류, 로그·감사 항목, 분류와 보존, 제한 정책의 근거를 기록한다. 모든 API에 임의의 고정 요청 수를 넣지 않는다. 실제 부하·위험·사용자 업무와 공유 식별자 경계를 확인하고 정한 제한을 검사한다.

SG2는 코드 분석 결과와 실제 동작 증거를 함께 본다. SQL 파일이 생성되었다는 사실, 정책 시뮬레이션 결과, 모의 객체만 사용한 테스트는 실제 DB 통과를 대신하지 못한다. 개인정보를 로그에 쓰지 않는지, 클라이언트에 비밀 키를 넣지 않는지, 일반 사용자가 관리자·다른 고객 데이터를 읽고 바꾸지 못하는지를 허용·거부 사례로 검사한다. 결과에는 기대·실제 반환 데이터와 상태, DB 변경 여부, 로그 확인을 남긴다. 거부 방식은 제품 계약에 따라 401/403/404 등으로 달라질 수 있으므로 숫자만 맞춰 통과시키지 않는다.

SG3는 납품 후보의 정확한 commit·빌드·의존성·검사 정책·환경을 다시 묶는다. 로그인 및 세션 만료, 익명 접근, A/B 사용자와 테넌트 간 교차 접근, 관리자 범위, 잘못된 ID, 대량 요청, 업로드 직접 접근 등 해당 제품의 부정 시나리오를 실행한다. IaC·배포 설정, DNS/TLS·공개 경로, 비밀값 참조, 백업·복구·인계 조건은 인프라 계약의 증거와 연결한다.

각 증거는 프로젝트·run·stage, 후보 manifest digest, commit SHA·base SHA, 테스트 모음·도구·정책·의존성 digest, 격리 대상 환경, 실행 시각·종료 코드·검사 수·실패·skip, 원본 결과 artifact digest와 발급자에 묶는다. 비밀값 원문과 실제 고객 레코드는 증거에서 제외하고 합성 자료를 사용한다. 코드뿐 아니라 검사·정책·환경·공급자 능력이 변경되어도 연결된 결과는 재검토한다.

기본 출시 정책은 미해결 Critical/High 및 필수 검사 실패가 있으면 보류다. 누락·0개 실행·무단 skip·오래된 결과·검증되지 않은 발급자·확인 불가도 통과로 간주하지 않는다. 오탐 판단은 위치·공격 경로·반증·검토자를 남긴 별도 기록이며 작성자의 선언으로 지적을 삭제하지 않는다. 허용 가능한 위험 예외가 있는 조직은 대상 후보·범위·사유·권한 있는 결정자·만료·보완 통제를 정책으로 한정해야 하며 예외를 테스트 PASS로 바꾸지 않는다.

Security Architect는 요구사항과 설계를, Security Tester는 승인된 격리 범위의 검사를, Security Reviewer는 증거와 차단 여부의 독립 검토를 맡는다. 논리적 역할이며 에이전트 세 개를 항상 동시에 호출한다는 뜻이 아니다. 자기 설계·코드·검사 결과만으로 독립 검토를 발급하지 못한다. 실제 신원·역할·중복 승인·재전송을 막는 집행은 후속 인증된 서버에서 구현해야 한다.

## 추적망과 직원 화면

향후 추적망은 SRC → REQ → SEC → 정책/자원/API/화면 → 보안 테스트 → Gate → 릴리스를 연결한다. 연결된 개수는 안전성이나 검사 실행률이 아니다. 현재 `channelshift.traceability/v1` 영향 분석은 field/api/backend/screen/test만 지원하므로 SEC·정책·Gate 노드를 그대로 가져올 수 없다. 확장 스키마와 호환성 검사를 별도 구현하고 기존 그래프는 보존한다.

직원 화면에는 확인한 범위·미확인 범위, 문제와 관련 기능, 기대·실제 동작, 배포가 보류된 이유, 다음 수정 작업을 보여 준다. 기술 식별자·CWE·원본 로그는 상세에 둔다. 현재 프로필의 검사 상태는 `not_invoked`, 연결은 false다. 실제 분모·완료 정의·측정 시점이 없는 92%나 합성 예시의 PASS 표시는 제품 결과로 사용하지 않는다.

## 출시 전 구현 완료 기준

1. 원문 근거와 내부 기준이 분리된 SEC, 신뢰 경계와 데이터 분류, 공급자 중립 정책을 버전으로 보관한다. 모델이 자기 승인자를 정할 수 없다.
2. 허용된 격리 DB에서 일반 사용자·교차 사용자·관리자·DB 우회 역할의 검사 영수증을 생성하고, 능력 불일치나 클레임 출처 불명은 보류한다.
3. 신뢰된 검사기와 독립 검토자의 동일 후보 증거만 SG1/SG2/SG3에 채택한다. 직접 API 호출·stale 탭·재전송·검사 발급자 위조를 검사한다.
4. 외부 코드 변경·정책 변경·비밀 버전 변경에서 승인과 배포 가능 상태를 재평가한다. 이전 SHA의 성공 체크로 새 코드를 배포할 수 없어야 한다.
5. 배포 후 감사 이벤트·알림 실제 수신·취약점 접수·영향 릴리스 추적·수정·재검수·재배포·복구 안내를 확인한다. 로그의 토큰·개인정보 최소화와 보존·삭제도 검사한다.

이번 변경의 단위 검사는 계획 DAG, Source 0, 기존 단계 ID와 계약 보존, 보안 단계 선행 조건, 미실행 표시만 확인한다. 위 완료 기준의 실제 실행 증거는 아직 없다.
