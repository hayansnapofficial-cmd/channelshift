# ChannelShift 제작 작업실

고객 원문을 넣고, 회원 본인의 Codex가 질문과 요구사양을 정리하며, 확인된 산출물을 다음 공정의 입력으로 사용한다. 기존 회원 데이터와 요구사항 이력은 보존하고 기본 화면과 진행 제어를 새 작업실로 교체한다.

## 공정

요구사항과 답변 → 요구사양 확정 → 화면 설계 검수 → ERD 검수 → API 계약 검수 → SQLite 구축 검증 → 백엔드 코드 검수 → 프론트 코드 검수 → 납품 검수·파일 묶음.

화면에서는 요구사항 / 화면 설계 / 데이터 / 백엔드 / 프론트 / 검수·납품의 여섯 구역으로 묶는다. 설정과 연결은 계정 패널에 둔다. 생성·검수는 사용자가 명시적으로 진행하고, 현재 단계의 산출물과 다음 행동을 보여준다.

## 필수 운영 정보

판매·서비스·SaaS 모두 사업자정보, 개인정보처리방침, 통신판매업정보, 고객문의, 호스팅사, 서비스 이용약관, 취소/환불 규정을 제품의 필수 납품 항목으로 적용한다. 설계 중에는 빈 초안을 저장할 수 있지만 완성된 납품 파일은 일곱 항목 모두 필요하다. 입력값을 그대로 안전하게 렌더링하며 사업자 사실이나 정책을 모델이 만들어 채우지 않는다. 작성 완료와 법률 검토 완료는 구분한다.

## 저장과 검수

기존 DeliveryWorkspace는 원문·질문·답변·ERD 어댑터로 유지한다. 새 PipelineWorkspace가 회원별 DB에 확정 사양, 공정별 파일, 입력 해시, 검수 기록을 저장한다. 검수는 로그인한 작업자의 판단이고 고객의 서명이나 동의로 해석하지 않는다. 변경 전후 기록과 작업자가 개입한 이유를 남긴다. 상위 사양·ERD·산출물이 바뀌면 하위 검수는 무효가 된다. 오래된 탭은 갱신 전 저장할 수 없다.

## 실행 경계

첫 실행 가능한 출력 형식은 Python 표준 라이브러리 + SQLite + HTML/CSS/JavaScript다. Codex는 제한된 파일 목록을 만들며 호스트에서 생성된 명령을 실행하지 않는다. SQLite DDL은 검증된 ERD에서 결정적으로 생성하고 별도 메모리 DB에서 실제 검사한다. 백엔드·프론트 검사는 구문과 계약 구조 검사이며 애플리케이션 실행·보안 감사·운영 배포 완료로 표시하지 않는다. 검수한 파일과 운영 정책, 검사 증거, 실행 안내를 ZIP으로 내려받는다. 운영 인프라 연결 및 실제 애플리케이션 인수 검사는 별도 실행 환경에서 수행해야 한다.

## 검증 계획

질문 답변의 재분석, 필수 항목 누락, 이전 탭 쓰기, 동시 생성, 생성 실패, 상위 변경에 따른 하위 검수 무효화, 회원 격리, 아카이브 경로, 실제 SQLite 검사, 정책 파일 포함, 작업 화면의 키보드·모바일·브라우저 흐름을 확인한다. 테스트용 모델 응답과 실제 Codex 호출을 구분해서 보고한다.

## 추가 요청과 미리보기

고객의 추가·변경 요청은 새 SRC로 기록하고 원래 요청을 보존한다. 새 원문이나 답변이 생기면 재분석 후 확정하도록 강제한다. 화면 미리보기는 허용한 HTML·CSS만 렌더링하며 폼·스크립트·외부 자원 요청을 차단한 sandbox에서 표시한다. 실제 앱 동작 미리보기가 아니다.

ZIP에는 확정 요구사양, 단계별 검토 이유, 납품 검사 자료와 파일 해시가 포함된다. 중단된 생성 작업은 저장한 프로세스의 생존과 생성 시각을 확인해 죽은 작업만 실패 처리하고 재시도할 수 있게 한다. 다른 살아 있는 서버 작업을 회수하지 않는다.

## 구현 검증 · 2026-09-29

Python 테스트 451개 중 447개 통과, POSIX 전용 검사 4개는 Windows에서 건너뛰었다. 새 JavaScript 모듈 네 개의 구문 검사도 통과했다. 합성 회원·모델 응답으로 HTTP 회원 격리·CSRF, 질문 재분석, 단계 순서, 추가 요청, 변경에 따른 검수 무효화, 서버 중단 복구, 필수 정책과 ZIP, 미리보기 격리를 확인했다. 실제 Codex 생성 호출과 생성 앱의 실행·공개 배포를 검증한 결과는 아니다.
