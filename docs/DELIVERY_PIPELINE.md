# 신입직원용 홈페이지 납품 공정

상태: 2026-09-29 개발 브랜치의 설계 및 기반 계약. 공개 v0.1.0 릴리스나 자동 제작·납품 완료 보고서가 아니다.
목표는 신입직원이 자료를 입력하고 안내된 작업을 실행하며, 검수 증거와 운영 인계자료를 갖춘 **실제로 동작하는 홈페이지**를 납품하도록 돕는 것이다.
시작점은 **클라이언트 요구사항 원문의 자연어 접수 → 프로그램에서 본인 Codex 계정 연결 → 본인의 Codex 이용 한도 안에서 명세·코드·수정 후보 작성**이다. 원문 접수가 환경 점검·설계·코드보다 먼저다. 현재 [접수 파일럿](INTAKE_PILOT.md)은 기존 Codex 로그인을 활용한 요구사항 후보 작성, Jev 보조 판단, 사람 개입 기록을 연결했다. 전체 명세·코드 생성은 후속 범위다.
공개 가입·개인 작업공간을 갖춘 [회원 플랫폼](MEMBER_PLATFORM.md)은 이 작업을 담는 서비스다. 납품 공정이 중심이며 회원가입 자체가 최종 결과물은 아니다.
로컬 데스크톱·컴패니언에서 Codex App Server의 관리형 ChatGPT 로그인을 연결하고, 클라우드 회원 작업공간은 별도로 둔다. 상세 인증·실행 경계는 [Codex 연결 설계](CODEX_CONNECTION.md)를 따른다. 서비스 계정 공동 사용이나 API 과금으로의 자동 전환은 하지 않는다.

제품은 **요구사항 구조화 → 시스템 설계와 디자인 후보 검토 → 세 계약의 정합성 검사 → 구현·검수·납품**을 연결하는 제작 워크벤치다. 시스템 설계와 디자인을 두 경로로 나누며, 와이어프레임을 끝내야 도메인·ERD 설계를 시작할 수 있는 선형 공정으로 두지 않는다. 디자인 후보의 버전·미리보기·수정·승인 계약은 [디자인 후보 설계](DESIGN_CANDIDATES.md)를 따른다.

[보안 공정](SECURITY_DELIVERY.md)은 두 설계 경로와 제작·배포 전반에 걸친 Security Lane이다. Business/System/Design의 세 계약을 유지하고, 원문 근거·내부 보안 기준·위협 모델·공통 접근 정책을 묶는 Security Contract와 SG1·SG2·SG3를 추가한다. DB 공급자와 AuthZ, 실제 격리 DB 검사, GitHub App·웹훅·동일 SHA의 증거 경계는 [공급자 계약](PROVIDER_CONTRACTS.md)을 따른다. 현재 추가한 것은 계획과 완료 조건이며 실제 보안 검사·연결·승인 집행은 미구현이다.

## 범위와 현재 상태

첫 파일럿의 표준 프로필 후보는 **회사 소개 + 포트폴리오 + 문의 접수 + 관리자 로그인 + 문의 목록·상태 관리**다. 실제 고객 원문에서 정식 요구사항을 만든 뒤 적합성을 확인해 선택하며 고객 요청을 템플릿에 강제로 맞추지 않는다. 이전 [예약 설정 예시](examples/README.md)는 계약 설명용이다.
현재 실제 고객 원문은 접수되지 않았다. 합성 예시는 프로그램 검사에만 쓰며 고객 프로젝트 제작·납품의 근거가 아니다. 실제 파일럿은 고객 원문 접수부터 시작한다.
결제·정산, 운영 데이터 이전, 새 기술스택 자동선택은 별도 프로필과 검수 범위를 정한다. 정적 사이트도 승인된 별도 프로필이 있어야 DB/API를 N/A 처리할 수 있다.

| 구분 | 현재 제공하거나 구축할 범위 | 완료로 간주하지 않는 것 |
| --- | --- | --- |
| v0.1.0 기존 코어 | DB 모델 검증, 초기 SQL·Java 생성, 로컬 편집기·MCP·내용 해시 버전 저장 | SQL 실행, 실제 DB 구축, 로그인, 홈페이지 생성 |
| 이번 B0 기반 | 표준 공정 프로필, 입력 증거에 대한 순수 Gate 계산, 읽기 전용 CLI | 증거 진위 확인, 승인 발급, 워커 실행, 서버 권한 강제 |
| 초기 실행 파일럿 | 고객 원문 로컬 저장, 구독 Codex 후보 작성, Jev 보조 검토, 사람 개입 사유·작업 시간 기록 | 회원 인증, 전체 구축, 공식 승인, 자동 복구·배포 |
| 등록 연결 기반 영향 분석 | DB 필드 편집 전 구조와 연결 JSON을 기준으로 API·백엔드·화면·테스트의 직접·간접 영향 표시 | 코드 자동 탐색, 미등록 의존성 발견, 연결 완전성 증명, 후속 상태 자동 변경 |
| 디자인 스튜디오·계약 결합 | 아래 두 경로와 세 계약, 후보·미리보기·승인 방식의 설계 및 계획 메타데이터 | 디자인 후보 실행기, 격리 미리보기, 인증된 디자인 승인, 네 영역의 완성된 UI |
| Security Lane·공급자 계약 | SEC·위협·접근 정책, SG1/SG2/SG3와 격리 DB·백엔드 검사의 의존성 계획 | 정책 컴파일·DB 접속·SAST/SCA/DAST 실행·보안 PASS·GitHub 웹훅 집행 |
| B1/B2 후속 런타임 | 인증된 실행 요청, 작업·시도·산출물 등록, 신뢰된 검사·리뷰·승인, 서버 Gate 집행 | 문서나 프롬프트만으로 실행 시스템 완성 주장 |

B0의 `PASS`는 제공된 입력이 계산 규칙을 충족한다는 뜻이다. 입력 파일의 승인 표기만으로 실제 승인·배포 권한이 생기지 않는다.

## 두 설계 경로와 결합 Gate

공통 진입 순서는 `intake → environment_check → requirements → business_review`다. 고객 원문, 프로젝트 경계, 원문에 근거한 요구사항과 인수 조건을 확인한 뒤 시스템 설계와 디자인 작업을 나눈다. 선행 조건은 단계 목록의 표시 순서가 아니라 명시된 의존성으로 결정한다.

```text
고객 원문 접수 → 환경 점검 → 요구사항 정리 → 업무 계약 검토
                                              │
                    ┌─────────────────────────┴───────────────────────┐
                    │                                                 │
             [시스템 설계 경로]                                [디자인 경로]
              도메인 모델                                  화면 명세·와이어프레임
                    ↓                                                 │
                   ERD                                                │
                    ↓                                                 │
                 DB Schema                                            │
                    ↓                                                 │
               API Contract ──────────────────────────────────→ 디자인 후보
                    ↓                                                 ↓
            Backend Architecture                               격리 미리보기
                    ↓                                                 ↓
               시스템 검토                                       디자인 검토·선택
                    └─────────────────────────┬───────────────────────┘
                                              ↓
                               BUSINESS / SYSTEM / DESIGN 정합성 Gate
                                              ↓
                              SG1 ← 현재 위협 모델·공통 접근 정책
                                              ↓
               DB 구축·정책검사·검수 → 백엔드 구현·보안검사·검수 → 프론트 구현
                                              ↓
                   SG2 → 통합·화면 검수 → SG3 → 납품 후보 검수 → 배포·인계
```

`wireframe`은 업무 계약 검토가 끝나면 시작할 수 있다. 실제 `design_candidate` 생성에는 `wireframe`과 `api_contract`가 모두 필요하다. `contract_review`는 `system_review`와 `design_review`를 합치며 유효한 Business Contract도 함께 검사한다. 두 경로의 작업을 항상 동시에 실행한다는 뜻은 아니며 실행기·계정 한도·공유 파일 소유권을 지켜 배정한다.

업무 계약 뒤 `security_requirements`와 도메인 모델에서 초기 `threat_model`을 만들고, ERD와 함께 `authorization_policy`를 정의한다. DB·API 계약은 이 정책을 입력으로 삼는다. `security_design_review`(SG1)는 세 계약 정합성 검수와 최종 위협·정책 revision을 확인한 뒤 DB 구축의 선행 조건이 된다. `database_policy_tests`는 DB 검수 전에, `backend_security_tests`는 백엔드 검수 및 프론트 구현 전에 필요하다. 프론트까지 포함한 `security_implementation_review`(SG2) 뒤 통합검수를, `security_release_review`(SG3) 뒤 납품 후보 검수와 배포 승인을 계획한다. 배포 후 `operations_security`의 운영 준비 확인이 인수인계에 필요하다. 단계 ID의 상세 완료 조건은 [보안 공정](SECURITY_DELIVERY.md#의존성으로-연결하는-security-lane)을 따른다.

| 단계 ID | 필수 산출물 | 완료 조건 |
| --- | --- | --- |
| `intake` | 실제 SRC 원문과 출처·접수 기록 | 원문 존재; 없으면 환경 점검·설계·코드 작업 잠금 |
| `environment_check` | 담당자·저장소 기준선·본인 Codex 연결·허용 환경 | 접수 원문에 맞는 작업 경계와 실행 기능 확인 |
| `requirements` → `business_review` | SRC 인용을 가진 REQ, 업무 규칙·역할·범위·인수 시나리오 | 차단 질문·미분류 원문 해소, 내부 제안 구분, 업무 승인자의 현재 revision 확인 |
| `domain_model` | 업무 개념·행위·상태·소유권·관계 | 요구사항에서 개념을 도출하고 테이블로 옮길 의미 확인 |
| `erd` → `database_schema` | 관계 모델·데이터 사전·물리 타입·키·제약·보존 기준 | 개념과 저장 모델의 매핑, 소유권·무결성 일치; 실제 DB 실행은 아직 아님 |
| `api_contract` → `backend_architecture` | 권한·입출력·오류 계약, 서비스 경계·트랜잭션·모듈 설계 | 업무 동작 지원, 저장·응답 모델 구분, 계약 밖 필드·동작 없음 |
| `system_review` | 고정한 시스템 설계와 검사·독립 리뷰 | 차단 지적 해소, 정책상 필요한 기술 결정 유효 |
| `wireframe` | 화면 명세·동선·상태별 배치·지원 화면 크기 | REQ와 화면 연결, 로딩·빈 상태·오류·권한 상태·버튼 동작 정의 |
| `design_candidate` → `design_preview` | 기준 REQ·시스템·화면 revision에 연결된 후보와 격리 미리보기 | 공급자와 입력·결과 보존, PC·태블릿·모바일 및 상태별 확인 가능 |
| `design_review` | 선택한 후보·차이·수정 요청·디자인 승인 기록 | 현재 후보의 화면·UX·콘텐츠 범위를 사람이 확인; 이전 후보 승인 재사용 불가 |
| `contract_review` | 세 계약과 다대다 연결의 정합성 검사 | 필드·타입·업무·권한·화면 동작의 충돌 및 필수 연결 누락 해소 |
| `database_build` → `database_review` | 신규 migration·합성 seed·설치·업그레이드·제약 검사 | 허용된 격리 DB에서 재현, 단일 DB Writer, 필수 검사와 독립 리뷰 통과 |
| `backend_build` → `backend_review` | 서비스·인증·입력검증·업무 구현, 계약·통합 검사 | 채택한 API·DB 기준선 구현, 권한·실패·중복 처리 검증 |
| `frontend_build` → `acceptance` | 승인 디자인 구현·실제 API 연결·E2E·화면 검사 | 정상·빈 상태·오류·모바일·권한 흐름과 인수 조건 충족 |
| `release_review` → `deployment_approval` | 검증된 동일 빌드와 인계자료, 대상 환경별 배포 결정 | 필요한 인수 확인 유효, 릴리스·환경·작업·유효 기간 일치 |
| `deployment` → `handover` | 배포·smoke 영수증·운영 안내·수령 기록 | 배포 확인과 실제 인수 완료를 각각 확인 |

정합성 Gate는 이미 수행한 업무·시스템·디자인 검토를 다시 사람에게 승인시키는 일반 단계가 아니다. 정해진 자동 검사를 수행하고 충돌을 해당 계약의 소유자에게 돌려보낸다. 디자인을 고른 것만으로 DB 구축·프론트 구현·배포 권한이 생기지 않는다.

## 직원에게 보이는 네 작업 영역

| 영역 | 직원의 작업 | 보이는 결과 | 현재 상태 |
| --- | --- | --- | --- |
| 요구사항 | 고객 원문 입력·분석 요청, 후보·질문·범위 확인, 판단 이유 기록 | 원문 근거, 미결정 항목, 다음 확인 사항 | `/delivery` 로컬 접수 파일럿 구현; 공식 요구사항 승인은 후속 |
| 시스템 설계 | Domain·ERD·DB·API·Backend 검토, 필드 변경 영향 확인 | 설계 차이, 등록된 의존성, 충돌과 재검수 대상 | 기존 DB 편집기와 등록 연결 기반 영향 패널 구현; 전체 설계 영역은 후속 |
| 디자인 스튜디오 | 제작 방식 선택, 후보 비교, 기기별 미리보기, 자연어 수정·선택 | 후보 버전, 이전 안과 차이, 확인할 요구사항과 승인 범위 | 계약·계획 설계; 후보 생성·격리 미리보기·승인 UI 미구현 |
| 제작·검수 | 현재 작업·실패·수정 요청·최종 확인·배포·인계 | 실행 증거, 다음 행동, 납품 가능 또는 보류 이유 | 접수 작업 상태·시간·개입 기록 일부 구현; 전체 제작 공정은 후속 |

작업 카드에는 목적, 입력 자료, 짧은 작업 이해 요약, 변경 범위, 실행 버튼, 통과 조건, 결과와 다음 행동을 표시한다. 에이전트 내부 로그 대신 직원이 해결할 문제를 먼저 보여 주고 기술 상세는 펼쳐보기로 둔다.
예를 들어 실제 검사에서 미인증 문의 조회가 허용되었다면 관련 REQ·API·테스트, 기대·실제 결과, 백엔드 수정 요청을 보여 준다. 실행하지 않은 검사를 예시 체크표시로 통과 처리하지 않는다.

진행률 `82%`, API Coverage `100%`, 영향 항목 수는 화면 장식으로 만들지 않는다. 진행률은 고정한 작업 분모·완료 판정·가중치·측정 시점을 제시할 수 있을 때만 표시한다. 계획 변경 시 계산 기준도 새 버전으로 남긴다. 연결 커버리지와 실행 테스트 성공률은 구분하고 의미상 요구사항 충족을 같은 숫자로 표현하지 않는다. 측정 근거가 없으면 미확인 또는 null이다.

현재 영향 패널은 가져온 연결 JSON만 탐색한다. 기준 schema digest가 맞지 않거나 필드 연결이 없으면 `UNKNOWN`, 범위를 선언하지 않은 종류는 `PARTIAL`/미확인이다. 같은 필드의 연속 편집은 편집 전 기준을 유지하고, 다른 필드로 이동하거나 저장한 뒤에는 현재 구조와 기준을 다시 확인한다. 여러 필드를 바꾸는 기본 키 전환은 전체 영향 확인을 요구한다. 그래프의 범위 선언은 코드 전체를 조사했다는 증명이 아니다.

## 정본·버전·추적 가능성

세 계약이 구현의 기준이다. 계약의 정본과 사람이 읽는 문서·그림을 구분한다.

횡단 Security Contract는 세 계약을 대체하지 않는다. 세 계약·SRC/REQ·SEC·위협·접근 정책·공급자 능력·보안 기준의 정확한 revision을 함께 묶고 SG1에서 검토한다. 고객 SEC에는 실제 인용을, 내부 SEC에는 기준 버전·적용 근거를 기록한다. 현재 영향 그래프의 SEC/정책/Gate 노드 확장은 후속 구현이며 기존 네 종류의 영향 분석으로 보안 완전성을 주장하지 않는다.

| 계약 | 포함하는 내용 | 확정 경계 |
| --- | --- | --- |
| Business Contract | SRC·REQ·업무 규칙·사용자와 권한·범위·미결정 해소·인수 조건 | `business_review`에서 업무 승인자가 고정 revision 확인 |
| System Contract | 도메인 모델·ERD·DB Schema·API·Backend Architecture와 매핑 | `system_review`의 검사·독립 리뷰 및 필요한 기술 결정 |
| Design Contract | 선택한 디자인 후보·화면 명세·동선·기기별 상태·콘텐츠·디자인 기준 | `design_review`에서 해당 후보 revision의 디자인 선택 승인 |

`contract_review`는 위 세 계약의 정확한 revision/digest를 하나의 후보 manifest에 묶는다. 업무 계약에 없는 회원가입을 추가하거나, 계약에 없는 테이블을 만들거나, 프론트가 API에 없는 필드를 요청하면 원인 계약으로 돌려보낸다. 어느 한 계약의 승인으로 다른 계약의 누락을 덮지 않는다.

고객 저장소의 제안 경로는 `delivery-spec/`다. 요구사항·인수 시나리오·결정·화면·디자인 기준·데이터 모델·API·추적 연결을 보관하며, 제품 코드와 migration은 선택한 프로필의 기존 경로를 따른다.
고객 원문은 SRC ID·version·digest·접수자·시점·출처를 기록하고 업무상 보존 기간에는 덮어쓰지 않는다. 정정·요약·마스킹은 연결된 새 버전 또는 파생본으로 남긴다. 이 불변성은 정해진 보존 만료·개인정보 삭제 정책을 막거나 영구 보존을 약속하지 않는다.
구조화 요구사항이 정본이고 Markdown은 읽기용 표현이다. API는 채택한 계약, DB 구현은 프로필이 선택한 ORM schema 또는 SQL migration 체계 하나를 정본으로 둔다. ERD 그림은 정본 모델에서 만든다.
REQ의 `source_refs`는 원문 SRC 버전과 정확한 인용 구간·문구를 가리킨다. 내부 제안은 별도 출처·상태로 두고 고객 확인 전 고객의 필수 요구사항으로 승격하지 않는다. 원문이 요구사항 정리의 근거이며 모델 요약이 원문을 대체하지 않는다.
산출물은 `artifact_id + revision + content_digest + source_refs + producer_attempt`로 식별한다. 과거 버전을 덮어쓰지 않는다.

검수 대상 manifest에는 다음을 묶는다.

- Git SHA와 dirty diff digest 또는 불변 snapshot, Business/System/Design Contract와 요구사항·화면·디자인 후보·API·DB revision.
- 의존성 lock·테스트 모음 digest, 검사 정책 버전, 실행 환경·도구 버전.
- 비민감 설정 fingerprint와 secret version 참조, 검사·리뷰·승인 기록 참조.
- Security Contract·공통 AuthZ·공급자 능력·GRANT/RLS·보안 검사 환경의 revision/digest, 신뢰한 검사 발급자와 GitHub installation/repository/PR/head·base SHA.

Gate 결과와 승인은 **그 manifest에만** 유효하다. 코드·테스트·계약·디자인 후보가 바뀌면 이전 증거를 새 후보의 증거로 사용할 수 없다. 같은 이름의 디자인이어도 새 revision에는 이전 선택 승인이 자동 상속되지 않는다. 비밀값은 manifest에 넣지 않는다.
`SRC-001 → REQ-INQ-001 → SCREEN-CONTACT → API-INQ-CREATE → TABLE-INQUIRY → BACKEND-INQUIRY → TEST-INQ-SAVE → RELEASE-001`처럼 원문에서 릴리스까지 연결한다.
연결은 다대다다. 한 요구사항에 여러 화면·API·테스트가 연결될 수 있고, 정적 문구 등에 불필요한 DB/API를 만들지 않는다. N/A에는 프로필 근거와 적용 불필요 결정 기록이 필요하다.
연결이 있다는 사실과 구현 정확성은 별개다. 필수 테스트 0개·누락·무단 skip은 차단하며 실제 인수 시나리오가 실패하면 통과하지 않는다.
납품 전 모든 원문 항목을 채택·질문·중복·확인된 제외 등으로 분류해 미분류를 남기지 않는다. 분류·참조 존재는 자동 검사할 수 있지만 의미상 누락이 없다는 사실은 자동 증명할 수 없으며 원문 대조와 고객 확인 근거가 필요하다.

## 자동 검사·독립 리뷰·사람 승인

Gate는 필수 산출물 유효, 선행 Gate 유효, 기준선 일치, 필수 자동 검사 통과, 차단 지적 없음, 필요한 독립 리뷰와 사람 승인의 유효성을 모두 확인한다.
자동 검사는 문법·타입·계약·정해진 테스트를 판정한다. 독립 검수자는 후보를 읽고 의미적 누락·모순을 지적하며 결과 코드를 직접 수정하지 않는다. 작성자는 같은 후보의 독립 검수자를 겸하지 않는다.

| 역할 | 결정할 수 있는 것 | 경계 |
| --- | --- | --- |
| 작업 담당 신입 | 자료 입력, 승인 범위 내 실행·수정·검수 요청 | 자기 최종 승인이나 임의 운영 배포 불가 |
| 업무 승인자 | Business Contract의 범위·고객 정책·범위 변경 | 실패한 필수 검사를 PASS로 바꿀 수 없음 |
| 디자인 승인자 | 현재 Design Candidate의 화면·UX·콘텐츠 범위 선택 | 디자인 변경 시 재확인; 업무·기술·배포 승인 대행 불가 |
| 기술 승인자 | 표준 밖 설계, 인증·DB 등 고위험 변경 | 검토 근거와 대상 revision 기록 |
| 배포 승인자 | 특정 릴리스·환경·작업·유효 기간의 배포 | 포괄적 무기한 승인 불가 |
| 고객·인수 담당 | 업무 시나리오 확인, 인계 수령·인수 | 시스템이 확인을 대신 만들어내지 않음 |

업무 계약 검토와 디자인 선택은 각각 필요한 사람이 결정한다. 시스템 검토와 G2/G3는 자동 검사·독립 리뷰를 수행하고 정책상 필요한 예외만 기술 승인자에게 보낸다. 두 설계 경로를 합치는 G2A 정합성 Gate는 자동 검사다. 모든 클릭에 사람 승인을 요구하지 않는다. G4 확인과 배포 권한은 별도다.
B1/B2에서는 인증된 서버가 직접 API 호출·다른 세션·재전송에도 같은 규칙을 적용한다. 워커의 `PASS`·`approved: true`, 요청 본문의 승인자 ID는 권한 증명이 아니다.

SG1·SG2·SG3는 보안 설계·구현·배포 후보의 독립 검토를 각각 요구한다. 누락·오래된 증거·0개 실행·무단 skip·필수 검사 실패·미해결 차단 지적은 통과가 아니다. 코드 작성자와 검사 결과 발급자를 신뢰한 독립 검토자와 구분한다. GitHub 웹훅은 서명·저장소·중복 검증 후 정본 상태를 다시 조회하는 신호이며, 이전 SHA의 green 체크나 webhook JSON의 승인 문자열로 새 후보를 승인하지 않는다.

## 수정·재시도·중단·복구

표시 상태는 `LOCKED → READY → RUNNING → VERIFYING → REVIEW_PENDING → 필요 시 APPROVAL_PENDING → ACCEPTED`다. 실패는 `NEEDS_FIX`, 결정 부재는 `NEEDS_DECISION`, 기준선 변경은 `STALE`로 표시한다.
실행 성공과 단계 승인, `DELIVERY_READY`와 `RELEASED`와 `DELIVERY_ACCEPTED`를 구분한다. 배포 성공만으로 고객 인수 완료가 되지 않는다.
프론트 작업 중 파일 첨부 기능을 추가한다면 ChangeRequest로 범위·저장소·권한·보존기간·비용을 확인한 뒤 관련 요구사항·화면·API·DB·테스트를 새 revision으로 만든다.
의존성을 따라 영향받는 후속 단계와 증거를 STALE로 표시한다. 무관한 산출물은 영향 없음의 근거를 남겨 재사용한다. 영향 분석이 불완전하거나 인증·공통 계약이 바뀌면 재검수 범위를 넓힌다.
자동 수정은 **최초 포함 총 3개 Attempt**를 제안 기본값으로 둔다. 실측 성능값이 아니며 오류·변경·검수 결과를 보존한다. 같은 오류 반복·범위 확대·승인 필요 변경은 한도 이전에도 멈춘다.
Provider 장애·인증 만료·본인 Codex 한도 도달을 구분하고 로그인 복구·한도 초기화 후 같은 작업을 재개한다. 다른 사람 계정·서비스 계정 풀·API 과금으로 자동 전환하지 않는다. 관측할 수 없는 비용·잔여량은 사유와 함께 null로 둔다.
일시정지는 새 배정을 멈추고 실행기가 지원하는 안전한 경계에서 정지한다. 취소 후에는 자식 프로세스 종료와 부작용을 확인한다. 지원하지 않는 중간 정지를 제공한다고 표시하지 않는다.
재시작 시 이전 프로세스·lease·파일 digest·migration 이력·외부 작업 영수증을 대조한다. **이전 Writer가 멈췄다는 증거 없이** 만료 시간만 보고 새 Writer를 배정하지 않는다. 확인 불가는 `RECOVERY_REQUIRED`다.
상태 전이는 트랜잭션과 이벤트로 기록하고 `expected_revision`, `idempotency_key`로 중복 실행·동시 승인을 제어한다. 이는 후속 런타임의 요구사항이며 현재 로컬 저장기의 보장으로 간주하지 않는다.

모듈은 하나의 서비스 안의 책임 경계다. 모듈마다 범용 서버·스케줄러·로그인·상태 DB를 따로 만들지 않는다. 장기 작업은 검증된 실행기 경계로 넘기며 HTTP 요청 안에서 계속 실행하지 않는다.

| `src/channelshift/web.py`, `web/` 및 회원 서비스 경계 | 기존 DB 편집기·로컬 접수·영향 패널 구현; 네 작업 영역 전체와 인증된 회원 명령 API는 제안 |

현재 `ProjectStore`는 2 MiB 네이티브 schema 제한과 10,000개 파일 탐색 제한을 가진 로컬 저장기다. 큰 증거·이미지·릴리스·승인 이력을 억지로 넣지 않는다. 내용 해시는 소유권이나 승인 진위의 증명이 아니다.
첨부에서 언급한 PhotoShift/Foundry의 Task·Adapter·권한·이벤트 엔진은 이 저장소에서 확인되지 않았다. 존재하는 통합 대상으로 표현하지 않고 B0 조사에서 실제 재사용 가능 여부를 먼저 확인한다.
사용자가 지정한 `weding-eoduksini-adapter/orchestration/harness-v1` 경로는 존재하며, README·스키마를 읽기 전용으로 확인했다. README에 명시된 기준은 `uumm123331/wedding`, commit `e479e1fdcf35f052681a4a301cb640a71d65c122`, 2026-08-28이다. 확인된 자료는 PhotoShift 저장소에 맞춘 오케스트레이션 하네스와 정적 검증 도구 묶음이다. 독립적인 Task/Attempt/Provider 저장·스케줄링 서비스는 이번 확인 범위에서 검증하지 못했다. 현재 저장 계약과 직접 호환되지 않으며 코드를 가져오지 않았다. Jev(TypeSafe)는 접수 후보의 의미 검토 API로 연결했고, 판정은 승인 권한을 갖지 않는다.

## 데이터 권한과 납품 조건

사람이 개입한 단계·원인·상황·결정·결과를 작업·원문·후보 버전에 연결한다. 고객 자료 부족, 요구사항 모순, AI 오류, 표준 밖 요청, 권한 확인, 품질 문제를 구분한다. 실행 시간·실패·수정 후 결과와 함께 분석해 자동화 범위와 선임 검토 범위를 조정한다. 개입 감소만을 품질 향상으로 간주하지 않는다. 현재 로컬 기록은 인증된 승인자 신원의 증명이 아니다. 실행기 API는 이전 원문·후보·개입 사건을 덮어쓰지 않고 새 사건을 추가하며 정정도 새 기록으로 연결하는 것이 원칙이다. 로컬 OS 사용자가 DB를 직접 바꾸는 것까지 방어하는 감사 저장소는 아니다. 보존 만료·허용된 삭제 정책을 별도로 적용해야 하며 현재 파일럿에는 원문 수정·삭제·보존 만료 API가 없다.

회원 플랫폼의 자료 보관·공개·공용 템플릿·AI 활용 권한 구분을 그대로 적용한다. 고객 홈페이지 제작 권한을 다른 회원용 재사용 권한으로 확대하지 않는다. 로컬 작업 자동 업로드나 실제 업무 원문 수집도 기본 동작이 아니다.
합성 데이터로 검증하고 로그·스크린샷·trace의 개인정보·토큰은 제한·마스킹한다. 일반 워커는 운영 DB·배포 키·승인 저장소·게이트 정책을 수정할 수 없도록 런타임 경계에서 집행한다.
인수 검사는 문의 저장, 관리자 조회, 상태 변경 후 새로고침 유지, 미인증 접근 거부, 입력 오류·중복 제출을 포함한다. 내부 API를 전부 mock으로 바꾼 결과는 최종 통합 증거가 아니다.
화면은 승인된 지원 기기·브라우저에서 키보드 조작·레이블·대체텍스트·반응형·오류 상태를 확인한다. 고객 문구·사진·로고 권한, 연락처·가격·주소의 정확성, 임시 문구 제거는 사람이 확인한다.
배포 승인은 `release_id + build_digest + target_environment + 수행 작업 + 유효 기간`에 묶는다. 같은 검증 빌드를 배포하며 재빌드는 새 후보로 검수한다. 환경변수·DB 연결·도메인/TLS·관리자 접근·smoke 결과를 확인한다.
DB 복구와 코드 되돌리기는 구분한다. 데이터 손실 가능성이 있는 복구는 변경별 계획·백업·권한을 확인한다. smoke 실패나 인계 누락이면 인수 완료로 전이하지 않는다.
인계 묶음에는 소스 commit/tag, 빌드·배포 정보, 요구사항·화면·API·DB 문서, 검사·변경 기록, 관리자 사용법, 백업·장애 복구 안내, 계정·도메인·호스팅 소유자, 유지관리 범위·알려진 제한·인수 확인을 담는다. 비밀번호·API 키 원문은 제외한다.

프로젝트 목록과 실제 고객 작업의 시작 조건은 [프로젝트 목록 계약](PROJECT_CATALOG.md), SEO·OG·실제 렌더링 HTML·DNS/TLS·기존 메일 레코드 보존은 [인프라·납품 계약](INFRASTRUCTURE_DELIVERY.md)을 따른다. DNS 변경 전 snapshot·변경 diff·대상 권한·승인과 변경 후 readback을 분리하고, 유효한 TLS·redirect·공개 경로를 확인한다. 납품에는 소유권, 백업 복원 근거, 안전한 비밀값 인계, 임시 접근 회수, 고객 인수의 증거가 필요하다. 프로필에 증거 이름이 있거나 URL 문자열을 검사한 것만으로 실제 DNS·OG·복구·인수를 확인한 것은 아니다.

## 구축 순서와 완료 증거

| 순서 | 구축 범위 | 확인할 결과 |
| --- | --- | --- |
| B0 | 실제 구조 매핑 + 표준 프로필·Gate 순수 계산 기반 | 재사용·미구현 목록, 같은 입력의 재현 가능한 판정, 기존 DB 코어 유지 |
| B1 | 본인 Codex 로그인·고객 원문 접수, 한 작업의 수명주기와 최소 화면 동선 | 실제 원문에서 요구사항 확정 후 적합한 문의 API 작업의 실행·실패·후보 등록·재시도 표시 |
| B2 | 신뢰된 증거·독립 리뷰·승인 binding·서버 Gate | 이전 후보 승인, 자기 리뷰, 직접 API 우회, 중복 명령 차단 |
| B3 | 시스템·디자인 두 경로와 세 계약, 횡단 보안 계약·SG1/SG2/SG3, 공급자·실제 정책검사 연결 | 승인한 디자인·시스템·권한 계약으로 합성 DB의 문의 흐름과 교차 사용자 거부 실제 동작 |
| B4 | 변경·중단·복구 | 후속 단계 STALE, 총 3회 정책, 이전 Writer 확인 후 재개 |
| B5 | 환경별 배포와 인계 | 승인된 테스트 환경 배포·smoke·수령 기록 |
| B6 | 신입 파일럿 | 안내만으로 표준 사이트 완료, 시니어가 대신 고친 구간과 보완점 기록 |

제품 완료는 신입이 다음 행동을 추측하지 않고 진행하고, 시스템이 근거 없는 완료를 차단하며, 실제 홈페이지와 인수 증거가 함께 남는 상태다. 문서 수·에이전트 수·코드 줄 수로 완료를 대신하지 않는다.

근거: 제공된 초기 설계·v1.1 요약과 2026-09-29의 두 설계 경로·디자인 후보·세 계약·네 작업 영역 요청을 현재 Python 저장소에 맞춰 반영했다. 초기의 와이어프레임 우선 선형 순서는 이 문서의 의존성 구조로 대체한다. 확인한 하네스는 저장소별 검증 도구 묶음이며 재사용 Task 실행 엔진으로 검증된 것은 아니다. 계획·문서·메타데이터는 전체 제작 런타임의 완료 증거가 아니다.
