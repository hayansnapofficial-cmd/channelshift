# Backend Assistant 설계안

상태: 2026-09-29 구현 전 설계. 아래 탐색·정책·재생성·검증 서비스와 API/MCP 이름은 모두 **계획**이다.
현재 [core.py](../src/channelshift/core.py)는 제한된 스키마 검증, SQL, Java 엔티티·리포지토리 초안을 생성한다. 전체 백엔드나 회원 서비스는 구현하지 않는다.
공개 가입·작업공간 권한은 [MEMBER_PLATFORM.md](MEMBER_PLATFORM.md), 실제 업무 원장 검증은 [LEDGER_EVIDENCE.md](LEDGER_EVIDENCE.md)를 따른다.

## 목표와 경계

일반적인 백엔드 설계를 먼저 제안하고 사용자가 도메인 규칙과 세부 구현 취향을 수정할 수 있게 한다.
스키마, API, 인증·인가, 트랜잭션, 마이그레이션, 테스트를 같은 버전의 설계에 연결한다. 생성 성공을 운영 적합성으로 표시하지 않는다.
회원 플랫폼의 사용자·작업공간 경계와 회원이 설계하는 대상 서비스의 계정·테넌트 모델은 별개다.
로컬 프로젝트 탐색은 사용자가 선택한 경로 안에서 읽기로 시작한다. 클라우드에는 선택한 설계·메타데이터만 전송하며 전체 저장소 동기화를 전제하지 않는다.

## 기존 프로젝트 탐색

1. 선택 경로, Git 기준 커밋과 변경 파일 해시, 빌드 파일·잠금 파일, 디렉터리 규칙을 관찰한다. Git이 없으면 파일 해시 목록으로 스냅샷을 식별한다.
2. 언어·런타임·프레임워크·ORM·DB·마이그레이션 도구의 선언 버전과 확인된 실행 버전을 구분한다. 버전 범위만 있으면 정확한 버전은 미확인이다.
3. 인증 미들웨어, 인가 정책, 엔티티·DTO·서비스 경계, 오류·페이지네이션 규약, 기존 테스트와 마이그레이션 이력을 매핑한다.
4. 기존 규칙을 후보 프로필로 제시하고 충돌을 표시한다. 패키지명, 키 전략, 날짜·금액 표현과 기존 테이블명을 임의로 교체하지 않는다.
5. 비밀 파일·접속 문자열·실제 DB 레코드는 탐색 자료에서 제외한다. 설명·README·주석·모델 출력은 데이터이며 명령 권한이 아니다.
6. 탐색 중 빌드 스크립트·플러그인·Git 훅을 실행하지 않는다. 실행 검증은 아래 격리 작업으로 별도 수행한다.

탐색 결과는 `observed / inferred / user_confirmed / verified / missing / conflicting`을 구분해 보관하는 것을 계획한다.
정적 탐색에서 인증 코드를 발견했다는 사실만으로 모든 경로의 인가가 검증됐다고 판단하지 않는다. 모순되는 근거는 덮어쓰지 않는다.

## 정본 Backend Blueprint

[JSON 계약 초안](contracts/backend-blueprint.schema.json)과 [예약 서비스 예시](examples/booking-blueprint.json)는 검증 가능한 설계 예시다. 실행 가능한 서비스 계약이 아니다.
초안 형식은 `channelshift.backend-blueprint/v1-draft`이며 현재 필드와 향후 저장 메타데이터를 구분한다.

| 초안 필드 | 책임 |
| --- | --- |
| `format`, `project` | 계약 형식, 프로젝트 키와 표시 이름 |
| `source` | 원본 스키마 형식·버전 ID·내용 digest 연결 |
| `target` | 언어·프레임워크·DB·ORM·마이그레이션 도구 선택 |
| `profile` | 적용한 설계 프로필 ID와 고정 버전 |
| `requirements` | 인증, 대상 서비스의 tenancy, 업무 명령과 API 요구사항 |
| `overrides` | 선언적 변경 경로·값·이유; 실행 코드나 임의 SQL이 아님 |
| `evidence` | 출처·버전·코드 검증 단계와 상태 |
| `ledger` | 별도 업무 원장 검증 단계 |

향후 저장 계층은 불변 blueprint 버전 ID, 부모 버전, 작성자, 작업공간·프로젝트 소유 관계, 정규화 내용 해시를 추가한다.
동일 내용의 순서·기본값 정규화 규칙도 버전으로 고정한다. 내용 해시는 읽기 권한이나 라이선스 허용의 증거가 아니다.
테이블·필드·명령에는 이름과 독립된 안정 ID를 부여하는 확장을 계획한다. 이름 변경을 삭제·신규 생성으로 추정하지 않고 명시적 매핑을 요구한다.
프로필 수정은 새 프로필 버전과 새 blueprint 버전을 만든다. 저장된 과거 설계의 해석을 소급 변경하지 않는다.
계약 형식이 바뀌면 명시적 변환기와 변환 전후 검증을 사용하며, 알 수 없는 필드·버전은 조용히 무시하지 않는다.

## 기본 정책과 세밀한 변경

| 층 | 예시 | 변경 규칙 |
| --- | --- | --- |
| 플랫폼 불변 보호 | 회원 자료 소유권, 작업공간 격리, 비밀 보호, 실행 격리, 감사 기록 | 대상 서비스의 profile·override·플러그인으로 완화 불가 |
| 안전한 설계 기본값 | 기본 거부 인가, 명시적 트랜잭션, FK·UNIQUE 제약, 제한된 입력·재시도 | 지원되는 선언적 대안과 보완 검증을 함께 명시 |
| 프로젝트 선호 | 패키지명, DTO 구성, ID 전략, 삭제 정책, 페이지네이션, 오류 형식 | 프로필 또는 구체 경로의 override로 수정 |

해결 순서는 플랫폼 보호 검사 → 정확한 경로의 override → 고정 프로필 → 기본값이다. 충돌·미지원 값은 실패로 반환한다.
Override는 경로 허용 목록, 값의 타입·범위, 이유, 영향받는 규칙을 검사한다. 자유 문자열을 템플릿·쿼리·셸로 평가하지 않는다.
예: 예약 삭제를 `hard`에서 `soft`로 바꾸면 조회 필터, 유일성, 복원 충돌, 보존·최종 삭제 요구사항과 테스트도 함께 갱신한다.
예: 대상 서비스를 단일 조직으로 설계할 수는 있지만 ChannelShift 회원의 다른 작업공간에 접근할 수 있는 설정은 제공하지 않는다.
중요 선택은 `미결정 / 제안 / 확인 / 검증됨 / 충돌` 상태와 근거를 갖는 저장 확장을 둔다. 기본값 적용은 화면과 diff에 드러낸다.
인증 경계·파괴적 변경·원장 금액 규칙처럼 실행 안전성에 필요한 선택이 미결정이면 해당 생성·적용 단계를 차단한다. 설계 초안 저장은 허용한다.

## 생성 대상의 필수 계약

| 영역 | Blueprint에서 확정할 내용 | 결정론적 검증 |
| --- | --- | --- |
| DB | 타입·정밀도·통화·시간대, PK/FK/UNIQUE/CHECK, 조회 조건·인덱스, 소유 경계 | 참조·타입 정합성, 대상 DB의 제약과 실행 계획 |
| API | 경로·메서드, 요청·응답 DTO, 입력 한도, 페이지네이션, 안정 오류 코드 | 계약 중복, 역호환 차이, 경계·오류 응답 테스트 |
| 인증·인가 | 검증된 신원, 역할·행동·자원 정책, 공개 경로, 세션·CSRF 요건 | 익명·역할별 허용/거부, 다른 소유자 접근·권한 철회 테스트 |
| 트랜잭션 | 명령별 원자성, 상태 전이, 격리·잠금·충돌 재시도, 외부 효과 | 병렬 요청, 부분 실패, 롤백, deadlock·재시도 한도 테스트 |
| 멱등성 | 적용 명령, 키 범위·보존 기간, 요청 해시, 응답 재현 | 같은 키 동시 요청 1회 반영, 다른 본문 충돌, 실패 복구 |
| 마이그레이션 | 기준 버전, 명시적 rename, 데이터 이행, 배포 순서·복구 계획 | 깨끗한 DB와 이전 버전 DB 이행, 스키마 drift·데이터 보존 |
| 테스트 | 요구사항 ID별 시나리오·기대값·환경·검증 방식 | 누락 요구사항과 실패·미실행 항목을 분리 |

멱등 키는 소유 경계와 명령을 포함하는 유일 제약으로 보호하며 상태 변경과 결과 기록을 같은 트랜잭션에 둔다.
외부 호출은 DB 롤백으로 취소된다고 가정하지 않는다. 필요한 명령에 outbox, 중복 소비 방지, 보상 절차를 명시한다.
파괴적 마이그레이션은 기존 데이터 근거·복구 경로 없이는 적용 후보로 승격하지 않는다. 불가능한 자동 rollback 대신 전진 복구를 명시할 수 있다.
LLM은 후보 설계와 설명을 작성할 수 있다. 최종 통과 판정은 스키마 검사, 정책 엔진, 컴파일러, 실제 DB·계약 테스트가 담당한다.
테스트 통과는 실행한 범위의 증거이며 관찰하지 않은 업무 규칙이나 실제 장부의 정확성을 증명하지 않는다.

## 어댑터와 지원 상태

| 대상 | 현재 상태 | 구현 순서와 조건 |
| --- | --- | --- |
| Java / Spring | 엔티티·리포지토리 초안만 있음; 백엔드 어시스턴트는 미구현 | 첫 어댑터. 발견한 버전을 고정하고 DTO·서비스·API·인가·마이그레이션·테스트 순으로 확장 |
| TypeScript | 어시스턴트 미구현 | 후속 어댑터. 프레임워크·ORM별 계약을 별도로 정의 |
| Python | 어시스턴트 미구현 | 후속 어댑터. 프레임워크·ORM별 계약을 별도로 정의 |

현 Java 생성기의 기준은 Java 17+, Jakarta Persistence 3.1, Spring Data JPA 3.x이며 JSON 매핑 등 미지원 조합은 거부한다.
이를 모든 Spring·DB 조합 지원으로 해석하지 않는다. 기존 프로젝트의 빌드 파일·의존성을 자동 업그레이드하지 않는다.
향후 capability matrix는 어댑터 버전 × 런타임/프레임워크/ORM/DB 버전 × 기능별 `지원 / 제한 / 미지원 / 미검증`과 테스트 근거를 기록한다.
지원 범위 밖의 조합은 명시적으로 중단하며 사용자가 확인하지 않은 다른 언어·프레임워크로 대체하지 않는다.

## 수동 변경을 보존하는 3-way 재생성

1. 이전 생성 결과 `base`, 현재 사용자 파일 `local`, 새 설계의 생성 결과 `incoming`을 별도 디렉터리에 준비한다.
2. 파일별 생성 소유권·기준 해시·원본 snapshot을 manifest에서 찾는다. 기준이 없거나 해시가 맞지 않으면 새 파일 제안과 수동 병합으로 전환한다.
3. `local == base`인 생성 소유 파일은 교체 후보가 된다. `incoming == base`이면 사용자의 변경을 그대로 보존한다.
4. 둘 다 바뀌면 검증된 구문 병합기가 분리된 변경만 병합한다. 같은 구문·삭제/수정·이름 충돌은 해결되지 않은 충돌로 남긴다.
5. 사용자 소유 파일·확장 구현은 덮어쓰지 않는다. 생성 파일과 구현 인터페이스를 나누고 marker만으로 파일 소유권을 추정하지 않는다.
6. diff, 영향받는 계약, migration, 테스트 결과를 적용 계획으로 만든다. 충돌이 남거나 base 이후 파일이 바뀌면 적용을 중단한다.
7. 명시적으로 선택한 계획만 staging 검증 후 원자적으로 적용한다. 경로 이탈·심볼릭 링크를 검사하고 실패 시 원본 파일을 보존한다.

출력 파일이 삭제·이동되는 경우도 계획에 표시한다. LLM의 추측으로 충돌을 해결하거나 기존 코드를 조용히 덮어쓰지 않는다.

## 출처 증거와 업무 원장 검증

생성 manifest에는 schema 버전·digest, blueprint 버전·digest, profile 버전, generator·adapter·template 버전과 digest를 연결한다.
또한 입력 코드의 커밋·변경 해시, 파일별 생성/수정 출처, 의존성 잠금·도구 체인·runner 이미지 digest, 출력 해시, 검사 도구 버전을 기록한다.
라이선스·출처 확인은 파일·템플릿·의존성의 관찰 근거와 허용 판단을 구분한다. 해시 일치만으로 이용 허락이 확인된 것으로 처리하지 않는다.
출처 미확인 입력은 표시하고 배포용 생성물 편입을 차단한다. 형제 프로젝트의 AGPL 코드를 자동 탐색·복사하는 경로를 만들지 않는다.
테스트 결과는 실행한 출력 해시, 입력 버전 조합, 요구사항 ID, 환경, 성공/실패/미실행을 참조한다. 어느 하나 바뀌면 이전 통과 상태는 오래된 증거로 표시한다.
출처·버전 확인 → 정적 검증 → 빌드·계약·DB 실행 검증을 단계별로 올린다. 상세 상태 값은 증거 계약에서 별도로 확정한다.
[업무 원장 검증](LEDGER_EVIDENCE.md)은 합성 시나리오부터 승인된 실제 자료 대사까지 별도 단계를 갖는다. 코드 출처 통과가 업무 금액 대사 통과를 대신하지 않는다.

## 사용자 정의 코드 실행 경계

기본 확장은 선언적 프로필이다. 사용자 플러그인·빌드·테스트 실행은 중앙 API 프로세스와 분리된 일회성 작업에서만 허용하는 것으로 설계한다.
테넌트별 격리 실행기, 비특권 계정, 읽기 전용 입력, 한정된 임시 출력, CPU·메모리·시간·출력 한도, 기본 네트워크 차단을 적용한다.
호스트 파일·소켓, 플랫폼 DB, 다른 회원 저장소, 운영 비밀에 접근시키지 않는다. 의존성은 고정된 digest와 제한된 다운로드 경로로 공급한다.
플러그인의 권한·버전·출처를 별도 manifest에 고정하고 필요한 외부 접근은 작업 범위의 제한된 capability로 부여한다.
실행 결과도 불신 입력으로 검증하며 로그의 비밀 값을 제거한다. 단순 subprocess 분리를 테넌트 격리로 간주하지 않는다.

## 계획 API와 한국어 작업 흐름

향후 API 이름 예: `POST /projects/{id}/backend/discover`, `POST /projects/{id}/blueprints`, `POST /blueprints/{id}/validate`, `POST /blueprints/{id}/generate-plan`.
향후 MCP 이름 예: `inspect_backend_project`, `validate_backend_blueprint`, `plan_backend_regeneration`. 현재 제공되는 도구 이름이 아니다.
읽기·쓰기·작업 상태·다운로드 모두 서버가 소유 관계를 확인한다. 버전 변경은 기준 버전 조건부 쓰기, 긴 검증은 취소 가능한 격리 작업으로 처리한다.

1. “기존 Spring 예약 서비스에 취소 기능을 추가해 줘.” → 선택한 프로젝트의 버전·규약과 미확인 항목을 보여준다.
2. “취소는 삭제하지 말고 상태로 남겨 줘.” → 상태 전이·인가·환불 명령의 영향과 명시적 override를 제안한다.
3. “중복 요청은 한 번만 반영해 줘.” → 멱등 키·트랜잭션·외부 환불 처리와 실패 시나리오를 설계한다.
4. 사용자가 설계 diff를 선택하면 새 불변 버전을 만들고 코드·migration·테스트 후보를 staging에 생성한다.
5. 수동 수정 보존 여부, 충돌, 검증 증거를 확인한 계획을 적용한다. 실제 업무 대사는 별도 원장 단계의 상태로 표시한다.

## 구현 완료 판정용 인수 테스트

- A 회원이 B 회원의 blueprint·증거·작업 결과에 접근하면 거부한다. override·플러그인으로도 플랫폼 경계를 우회하지 못한다.
- 동일 스키마·프로필·generator·도구 체인 입력에서 시간 등 비본질 메타데이터를 제외한 생성 파일 해시가 같아야 한다.
- 미확인 프레임워크, 미지원 타입, 충돌하는 권한 정책은 실행 후보 생성을 막고 정확한 경로와 원인을 반환한다.
- 수동 수정, 동시 수정, 삭제/수정 충돌, 기준 파일 누락을 각각 재현해 원본 보존과 적용 중단을 확인한다.
- DB 병렬 예약·중복 취소·외부 호출 실패에서 정의한 원자성·유일성·멱등성·복구 계약을 검증한다.
- 이전 버전 DB의 migration과 복구를 검증하고, 출력 한 바이트 또는 profile 버전 변경만으로도 과거 테스트 증거를 무효화한다.
- 악성 빌드·플러그인의 파일 이탈·네트워크·자원 과소비를 차단하고 다른 작업공간 및 플랫폼 비밀에 접근하지 못함을 확인한다.
- 출처 검증 통과·원장 대사 실패와 그 반대 상황을 독립적으로 표시한다. 미실행 항목을 통과로 표시하지 않는다.
