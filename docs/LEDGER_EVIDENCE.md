# 설계 출처와 업무 원장 검증

상태: 구현 예정 설계. 기준일: 2026-09-29.
현재 v0.1.0의 로컬 스키마·해시 파일은 파일 일치 여부를 확인하는 기반이다.
회원 플랫폼, 전자서명, 외부 앵커, 업무 수집기, 거래 대사는 구현·운영 완료로 간주하지 않는다.
이 문서는 두 단계를 정의하며, `MEMBER_PLATFORM.md`의 플랫폼 설계와 함께 구현할 계약이다.

## 1. 두 단계와 증명 범위

| 단계 | 검증 대상 | 결과에 포함할 범위 | 증명하지 못하는 것 |
| --- | --- | --- | --- |
| 1. 설계·코드·버전 출처 | 설계 파일, 소스 리비전, 빌드 산출물 | 파일 식별, 승인 기록, 빌드 입력·실행자·버전 연결 | 설계의 우수성, 인간 저자의 진의, 실제 업무 거래 |
| 2. 업무 원장 | 예약·재고·정산 등 실제 업무 사건과 정정 | 수집 범위, 순서·무결성, 업무 규칙, 원천 대사 | 기록되지 않은 현실, 원천 시스템 자체의 허위 |

검증 결과는 `integrity`, `signer_policy`, `anchor`, `coverage`, `business_rules`, `source_reconciliation`으로 나눈다.
각 항목은 `pass | fail | unknown | not_applicable` 및 근거·검증 시각·정책 버전을 가진다.
서명이 맞아도 독립 원천을 확인하지 않았다면 거래 사실 검증은 `unknown`이다.
제품은 단일 “진실 인증” 배지 대신 검증된 기간·원천·항목과 미검증 구간을 표시한다.

## 2. 위협 모델과 신뢰 경계

| 위협 또는 주체 | 방어 수단 | 남는 한계 |
| --- | --- | --- |
| 클라이언트의 위조·다른 업체 ID 제출 | 서버 인증·객체별 인가·테넌트 격리·스키마 검증 | 정상 권한자의 허위 입력은 별도 대사 필요 |
| 수집 중 유실·중복·순서 역전 | 원천 위치·고유 ID·재시도·멱등성·대사 | 수집 전 사건은 범위 선언 없이는 알 수 없음 |
| 앱 계정의 과거 기록 수정 | 원장 UPDATE/DELETE 권한 제거, 제한된 append 경로 | DB 최고관리자에게는 별도 방어 필요 |
| DB 관리자의 전체 이력 재작성 | 분리된 서명 권한과 외부 체크포인트 대조 | 같은 관리자가 키·앵커까지 지배하면 방어 불충분 |
| 서명 키 유출 또는 악성 서명자 | 키 격리·회전·폐기·신뢰 정책·독립 증빙 | 유효한 서명도 내용의 진실성을 보장하지 않음 |
| 과거 정상 사본 재전송·꼬리 삭제·분기 | 최신 앵커·검증자 보관 위치·순번·연속성 대조 | 앵커 이후 구간은 최신성 보장이 제한됨 |

해시 연결만으로 사실·작성자·신뢰할 시각을 증명할 수 없고, 전체 이력을 다시 계산한 공격도 배제하지 못한다.
앵커 운영자, 검증자, 원천 제공자의 신뢰 가정을 명시하고, 모두 공모하거나 침해된 경우까지 보장하지 않는다.
원천 발생 시각, 수집 서버 시각, 외부 수신 시각을 분리한다. 외부 수신 시각은 그때까지 증거가 존재했다는 범위로 해석한다.

## 3. 1단계: 설계·코드·버전 출처

1. 설계 스냅샷에 schema/design 버전, 파일 목록과 digest, 상위 버전, 변경 사유를 부여한다.
2. 승인자는 인증된 주체와 승인 대상 digest로 기록한다. Git 작성자 문자열을 본인 확인 증거로 취급하지 않는다.
3. 소스 리비전과 빌드 설정·의존성 잠금 파일을 고정하고, 산출물 digest와 릴리스 버전을 연결한다.
4. 빌드 출처는 in-toto Statement와 SLSA Build Provenance를 사용한다. `subject`, `buildDefinition`, `runDetails`를 검증한다.
5. `predicateType`은 `https://slsa.dev/provenance/v1`이며, 허용된 signer-builder 조합과 입력 정책을 함께 확인한다.
6. 빌드 밖에서 작성된 설계·검토 승인은 별도 문서화된 predicate로 기록한다. 이를 SLSA 빌드 인증으로 표현하지 않는다.
7. 검증된 DSSE/attestation 도구로 서명하고, 신뢰 정책은 산출물과 독립된 경로에서 공급한다.
8. 검증자는 실제 배포·다운로드 파일의 digest부터 확인한다. 서명 파일만 검사하고 종료하지 않는다.
9. 재현 빌드는 별도 검수 항목이다. 출처 문서가 있다는 이유만으로 재현성 또는 SLSA 등급을 주장하지 않는다.

출처 형식과 builder의 신뢰 범위는 [SLSA Provenance](https://slsa.dev/spec/v1.2/provenance) 및 [Build Provenance](https://slsa.dev/spec/v1.2/build-provenance)를 따른다.
서명 문장의 대상 연결은 [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md)을 기준으로 한다.

## 4. 2단계: 업무 원장 규칙

- 원장은 사건을 추가한다. 오입력은 원본 참조, 사유, 권한 주체를 가진 취소·반대 분개·정정 사건으로 바로잡는다.
- 업무 엔터티의 현재 상태는 변경 가능하지만, 원장 사건과 연결하고 과거 사건의 덮어쓰기로 이력을 수정하지 않는다.
- 서버가 전이 규칙·버전 충돌·참조 무결성을 검사한다. 클라이언트가 계산한 잔액·권한은 신뢰하지 않는다.
- 통화는 통화 코드와 정수 최소 단위 또는 정밀도·스케일이 고정된 exact decimal로 표현한다. 부동소수점은 금지한다.
- API의 큰 정수·십진 금액은 문자열로 전달하고, 통화별 단위·반올림·초과 정밀도 거부 정책을 버전으로 고정한다.
- 복식부기는 금전 원장에 적용한다. 전표별·통화별 차변 합과 대변 합을 일치시키고 계정·전표를 같은 트랜잭션에 저장한다.
- 외화 교환은 명시적 환율·시각·반올림 조정 및 통화별 균형 전표로 처리한다. 서로 다른 통화를 단순 합산하지 않는다.
- 예약은 자원 중복·상태 전이, 재고는 수량·단위·입출고, 콘텐츠는 변경 버전 등 업무별 불변 조건을 둔다.
- 모든 업무를 복식부기로 강제하지 않는다. 선택한 도메인의 규칙 버전과 예외 승인 근거를 검증 보고서에 남긴다.
- 원천 증빙의 서명 확인과, 은행·결제·예약 등 별도 권한으로 읽은 원천 기록과의 대사는 구분한다.
- 같은 DB에서 생성한 영수증과 원장을 대조한 결과는 “독립 원천 대사”로 표시하지 않는다.

## 5. 수집·재처리·대사 계약

1. 자체 업무 변경과 outbox 삽입을 하나의 DB 트랜잭션으로 커밋한다. outbox 실패 시 해당 업무 변경도 롤백한다.
2. 발행기는 at-least-once로 전달하고, 소비자는 원장 append와 처리 위치 갱신을 같은 트랜잭션으로 커밋한다.
3. 외부 시스템은 승인된 API/webhook 또는 CDC로 수집한다. CDC의 행 변경은 업무 의미로 매핑하기 전까지 관측 기록이다.
4. `(tenant_id, connector_id, source_event_id)`를 고유 키로 한다. 같은 키·같은 내용은 기존 결과, 다른 내용은 충돌로 격리한다.
5. 수집 순번은 커밋 순서이며 발생 시각 순서를 가장하지 않는다. 늦게 도착한 사건은 원래 시각과 원천 위치를 보존한다.
6. 커넥터마다 시작 스냅샷, 스트림 전환 지점, 체크포인트, 허용 지연, 재조회 범위를 기록한다.
7. 누락은 ID·수량·금액·상태별 대사로 탐지한다. 웹훅 수신 성공만으로 완전성을 판단하지 않는다.
8. 중복은 멱등 처리하고, 정정은 새 원천 버전과 원본 사건 참조로 반영한다. 지연 건은 다음 대사에서 재검증한다.
9. 재시도는 제한·지수 지연·격리 큐를 사용한다. 큐 보존기간 만료 전에 경보를 내고 누락 범위를 명시한다.
10. 대사 결과는 `matched | missing | late | duplicate | corrected | conflicting` 및 원천 조회 범위·미해결 사유를 가진다.
11. 수집 중단 때 원천 업무의 지속 여부는 도메인별로 정한다. 검증 화면은 중단과 미검증 구간을 즉시 표시한다.

## 6. 제안 데이터 모델 — 모두 구현 예정

| 모델 | 필수 필드·제약 |
| --- | --- |
| `ArtifactVersion` | tenant, artifact_id, version, parent_id, files_digest, source_revision; 테넌트 내 버전 고유 |
| `Attestation` | subject_digest, predicate_type/version, envelope_ref, signer_identity, trust_policy_version |
| `LedgerStream` | tenant, stream_id, epoch, head_seq, head_digest; append 시 잠금 또는 CAS로 직렬화 |
| `LedgerEvent` | tenant, stream, epoch, seq, event_id, type/version, occurred_at, recorded_at, actor_ref, source_ref, payload_digest, prev_digest, event_digest |
| `Journal/Posting` | monetary domain 전용; journal_id, account_id, currency, debit/credit, amount; 균형 검사 후 원자적 확정 |
| `ConnectorCheckpoint` | tenant, connector, source_cursor, snapshot_ref, last_success_at, coverage_start/end |
| `AnchorReceipt` | tenant, stream, epoch, seq, head_digest, previous_receipt_digest, signer, external_receipt_ref, observed_at |
| `ReconciliationRun` | 원천·검증 범위, 기준 시각, 규칙 버전, 건수·합계, 차이 목록 참조, 상태 |
| `VerificationReport` | 대상 digest/범위, 여섯 검증 항목, 사용 앵커, 신뢰 정책 버전, 미검증 사유 |

모든 참조와 고유 제약은 테넌트 경계를 포함한다. 원장에는 `(tenant, stream, epoch, seq)` 및 `event_id` 고유 제약을 둔다.
epoch 재시작은 관리자 편의용 초기화가 아니다. 이전 최종 앵커와 새 시작점을 연결하는 승인된 전환 기록이 필요하다.

## 7. 무결성·외부 앵커 프로토콜

- 해시 대상은 알고리즘·스키마 버전, tenant/stream/epoch, seq, event_id, 사건 type/version, 시각·주체·원천 참조, payload_digest, prev_digest를 포함한다. 같은 본문을 다른 업무 사건으로 재해석하도록 종류·버전을 바꾸는 경우도 digest가 달라져야 한다.
- JSON은 검증된 표준 정규화 구현과 테스트 벡터를 사용한다. SHA-256 등 승인된 해시를 사용하고 자체 암호 알고리즘을 만들지 않는다.
- 해시 입력의 정확한 필드·문자 인코딩·null 처리 규약을 버전 관리한다. 같은 사건은 모든 검증 환경에서 같은 digest를 내야 한다.
- 체크포인트는 서명된 마지막 순번·digest·이전 영수증 연결을 포함하며, DB 관리자와 권한이 분리된 외부 저장소에 보관한다.
- 앵커 서비스는 이미 받은 동일 stream/epoch/seq의 다른 digest를 거부·경보하고, 이전 체크포인트와의 연속성을 검증한다.
- 검증자는 사전 등록된 테넌트·스트림 및 외부 최신 영수증과 이전 보관 위치를 독립 조회한다. 파일 안의 공개키·“최신” 표지만 신뢰하지 않는다.
- 분기 탐지는 검증자 간 체크포인트 비교 또는 투명성 로그의 일관성 검증을 포함한다. 단일 관측만으로 모든 분기를 발견할 수는 없다.
- 초기 운영 목표는 5분 또는 1,000건 중 먼저 도달할 때 앵커 발행이다. 실제 처리량 검수 후 정책으로 확정한다.
- 그 사이 구간은 `unanchored`로 표시한다. 만료·단절·누락된 영수증을 정상으로 낮춰 처리하지 않는다.
- 외부 장애 시 outbox에 대기시키고 지연을 표시한다. 위험 거래의 확정 보류 여부는 도메인별 승인 정책으로 정한다.
- 블록체인은 기본 의존성이 아니다. 독립 운영·비용·공개 범위가 필요한 경우에만 별도 결정한다.

## 8. 제안 API — 모두 구현 예정

| 경로 | 계약 |
| --- | --- |
| `POST /v1/artifact-versions` | 인가된 프로젝트에 스냅샷 등록; digest 서버 검증; Idempotency-Key 필수 |
| `POST /v1/artifact-versions/{id}/verify` | 대상 파일과 신뢰 정책을 검증하는 비동기 작업 생성 |
| `POST /v1/connectors/{id}/events` | 해당 테넌트·커넥터에 한정된 기계 인증; 원천 ID·버전·크기 검증 |
| `POST /v1/ledger-events/{id}/corrections` | 서버 도메인 규칙에 따라 원본 참조 정정 추가; 사유·멱등 키 필수 |
| `POST /v1/reconciliations` | 허용 원천과 기간의 대사 작업 생성; 비용·범위 제한 |
| `GET /v1/verification-reports/{id}` | 테넌트별 권한 검사; 여섯 검증 항목과 범위 반환 |
| `GET /v1/ledger-events` | 권한별 필드 필터와 순번 기반 커서 페이지; 원문 증빙 기본 제외 |

모든 쓰기는 동일 멱등 키·다른 본문에 409, 미인가에는 403 또는 존재 은닉 404, 형식·규칙 오류에는 422를 반환한다.
서버가 세션/기계 자격에서 테넌트를 결정한다. 임의 SQL, 임의 URL 수집, 일반 회원의 원장 직접 삽입은 허용하지 않는다.

## 9. 회원·관리자 로그와 개인정보

인증·권한 변경·관리자 조회·내보내기·키 작업은 보안 감사 로그로 분리하고, 업무 원장과는 불투명한 correlation ID로 연결한다.
회원 가입이나 관리자 로그인 성공은 실제 거래 증거가 아니다. 감사 로그도 별도 접근 통제·수집 장애 경보를 적용한다.
원본 업무 자료·개인정보는 테넌트가 소유·통제하는 저장소에 둔다. 외부 앵커에는 최소 체크포인트만 보낸다.
커넥터는 목적, 대상 시스템·필드·기간, 읽기/쓰기 범위, 보존기간, 해지 방법을 명시한 연결별 승인에 한정한다.
사용자의 원문·증빙을 다른 사용자 서비스나 교차 사용자 모델 학습에 사용하지 않는다. 분석·AI 처리는 별도 명시된 목적 범위만 허용한다.
불변 기록에는 비밀·토큰·이메일·전화번호·전체 요청 본문을 넣지 않는다. 필요한 사실과 불투명 참조로 최소화한다.
원문과 식별자 대응표는 별도 암호화·권한·유한 보존기간을 둔다. 단순 해시도 재식별 가능하면 익명화로 주장하지 않는다.
보존·삭제 요청 충돌은 데이터 유형별 정책으로 해결한다. 영구 보존을 기본값으로 하지 않고 원문·대응표·백업 만료를 함께 다룬다.
삭제·보존 만료는 승인된 폐기 기록과 대상 범위를 남기며, 삭제 후 원문 내용 검증이 불가능해진 사실을 보고서에 표시한다.
로그 최소화·보호·검증 기준은 [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)를 참고한다.

## 10. 키 운영과 출시 검수

서명 키는 KMS/HSM 등 검증된 관리형 기능에 두고 DB 관리자·앱 배포자·키 관리자 권한을 분리한다.
키 ID, 알고리즘, 유효기간, 회전·폐기·유출 시점을 관리하고 이전 공개키·신뢰 정책을 보존한다.
유출된 키로 만든 기록은 신뢰할 외부 시각과 사고 범위로 재평가한다. 과거 서명 성공만으로 안전 판정하지 않는다.
복구 시 백업 위치를 최신 외부 앵커와 대조하고 되감기·분기를 막는다. 키 손실·앵커 장애 복구 절차를 실제 연습한다.
키 수명주기는 [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html)를 따른다.

| 단계 | 완료 조건 |
| --- | --- |
| A. 계약 확정 | 한 업무 도메인·한 원천·책임자·보존기간·지연 허용치·신뢰 경계를 확정; 현재 로컬 검증의 한계를 표시 |
| B. 출처 검증 | 실제 산출물로 서명·허용 signer-builder·잘못된 대상·변조·키 교체 검증 통과; SLSA 등급은 별도 평가 |
| C. 업무 파일럿 | 테스트 테넌트에서 outbox·멱등·정정·도메인 규칙·독립 원천 대사 통과; 실거래 연결은 승인된 커넥터만 |
| D. 운영 검수 | 외부 앵커·키 분리·복구·삭제·권한 검수 및 운영 책임자 인수 완료 후 도메인별 제한 출시 |

필수 실패 주입: 본문 변조, 중간 삭제·순서 변경, 전체 재작성, 꼬리 삭제, 옛 사본 재전송, 동일 순번 분기를 각각 검사한다.
이미 앵커된 내용을 바꿔 재계산한 이력은 내부 해시 검사를 통과해도 외부 앵커와 불일치해야 한다. 앵커 없는 범위는 `unknown`으로 남긴다.
동시 append·중복 전달·동일 키 다른 본문·재시작·원천 지연·수집 단절·정정 재수신에서 누락·이중 반영이 없어야 한다.
불균형 전표·초과 환불·예약 충돌 등 선택 도메인의 불변 조건과 테넌트 간 조회·쓰기·증빙 유출 차단을 검증한다.
서명은 정상이나 원천 금액이 다른 사례, 원천 접근 불가 사례, 앵커 기한 초과 사례를 서로 다른 결과로 표시해야 한다.
성능·RPO·RTO는 파일럿 계측과 업무 요구로 수치 확정한다. 이 문서 작성만으로 위 검수나 실거래 검증이 완료되지는 않는다.
