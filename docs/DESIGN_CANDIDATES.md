# 디자인 후보·미리보기·선택 계약

상태: 2026-09-29 제안 설계. 디자인 후보 생성·격리 실행·기기별 미리보기·인증된 선택 승인 UI는 아직 구현하지 않았다. 현재 구현된 고객 원문 접수·Codex 요구사항 후보·Jev 보조 검토·사람 개입 기록·DB 필드 영향 패널과 구분한다. 전체 공정의 정본은 [홈페이지 납품 공정](DELIVERY_PIPELINE.md)이다.

디자인 제작자의 결과는 공통 **Design Candidate**로 접수한다. Codex가 작성한 화면 코드도 선택 전에는 후보이며, 사람이 제작한 Figma·이미지·코드도 같은 기준 참조·검토 절차를 거친다. 승인된 특정 디자인 revision이 Design Contract가 되고, 최종 시스템 계약과 정합성을 확인한 뒤 실제 프론트를 구현한다.

## 공정에서의 위치

```text
Business Contract 검토 완료
  ├─ Domain Model → ERD → DB Schema → API Contract → Backend Architecture → System 검토
  └─ Screen Spec·와이어프레임 ────────────────┐
                              API Contract ─┤
                                            ↓
                              Design Candidate → 격리 Preview → 디자인 선택·승인
                                            ↓
                    Business + System + Design 정합성 Gate → 실제 구현
```

화면 명세·와이어프레임은 업무 계약 검토 후 시스템 설계와 병행할 수 있다. 후보 생성은 화면 명세와 API 계약을 모두 입력으로 받는다. 코드형 디자인 후보는 합성 데이터로 격리 미리보기하기 위한 산출물이며, 이 단계에서 운영 백엔드·DB·배포를 실행하는 것은 아니다.
후보를 만드는 동안 시스템 검토가 진행 중일 수 있다. 이때 고정한 시스템 설계 manifest의 상태를 초안으로 표시한다. 세 계약을 합치는 Gate에서는 최종 수락된 시스템 revision과 후보 입력 참조를 대조하고, 달라졌으면 디자인 후보·승인·미리보기 증거를 새 기준에서 확인한다.

아래 항목은 후속 저장·실행 모듈의 계약 제안이며 현재 JSON API가 구현되어 있다는 뜻이 아니다.

출처 이름이나 원문 파일의 `approved: true`는 승인 증거가 아니다. 확인된 저장 경계에서 읽은 신원·역할·결정만 승인 정책에 사용할 수 있다. 콘텐츠 해시는 무결성 연결값이며 저작권·소유권·승인자 신원을 증명하지 않는다.
예시의 `Design v17 → v18`은 버전 관계 설명이다. 실제 후보를 17개 만들었다거나 검토했다는 뜻이 아니다.

## 제작 방식과 계정 경계

| 방식 | 기본 동작과 권한 | 현재 구현 여부 |
| --- | --- | --- |
| Codex | 작업자 본인의 기존 ChatGPT 구독 연결을 기본값으로 사용하고 현재 계약을 입력한다. 한도·인증·실행 기능을 확인한다. | 접수 요구사항 후보 작성만 연결됨; 디자인 생성 adapter는 후속 |
| Claude | 작업자가 선택하고 연결 방식·전송 범위·비용을 확인한 선택적 adapter다. | 미구현 |
| 디자이너 업로드 | 제공된 이미지·문서·Figma 내보내기·코드를 후보로 등록하고 기준 계약 및 사용 권한을 연결한다. | 미구현 |
| 기존 디자인 가져오기 | 허용된 출처의 디자인을 가져와 출처·재사용 범위·기준 버전·추가 기능을 확인한다. | 미구현 |

Codex 한도 도달이나 오류를 이유로 Claude·다른 사람 계정·서비스 계정 풀·API 과금으로 자동 전환하지 않는다. 후보 출처마다 같은 미리보기·수정·승인 인터페이스를 제공하되, 지원하지 않는 기능은 사용 가능하다고 표시하지 않는다.
Jev는 이미 연결된 선택적 유료 의미 검토 도구다. 디자인 제작자·실행기·승인자의 역할로 자동 승격하지 않는다. 외부 자료 수집이나 Figma 접근은 필요한 출처·계정 범위에서 별도로 수행하며 현재 후보 제작의 필수 의존성으로 두지 않는다.

## 격리 미리보기

Preview는 후보를 눈으로 보고 상호작용을 검토하는 실행 경계다. 가져온 코드·의존성·Figma 메타데이터·자산·문구는 신뢰되지 않은 입력으로 취급한다. 데이터 안의 명령이나 경로를 시스템 지시로 실행하지 않는다.

- 원본 고객 저장소와 다른 작업공간에서 실행하고, 후보 파일·합성 fixture·허용 자산만 제공한다.
- 운영 DB·배포 키·Codex 로그인 파일·회원 세션·원문 비밀값을 주입하지 않는다. 미리보기는 운영 변경 권한을 갖지 않는다.
- 호스트 설치 hook·임의 명령·파일 경로·외부 요청을 그대로 허용하지 않는다. 지원 빌드 도구·실행 명령·자원 한도·네트워크 허용 범위를 실행기에서 집행한다.
- 브라우저 미리보기는 별도 origin과 제한된 권한으로 제공한다. CSP나 iframe 속성 하나만으로 서버 코드까지 격리되었다고 판단하지 않는다.
- 후보별 빌드·환경·의존성·viewport를 기록한다. 새 빌드는 새 digest를 가지며 기존 승인 화면과 혼동하지 않는다.
- 이미지형 후보는 정적 시안이라고 표시한다. 클릭·API 동작을 실제로 검증하지 않았다면 작동하는 인터랙티브 미리보기로 표현하지 않는다.

위 실행 경계는 후속 구현 사항이다. 현재 DB 편집기나 접수 파일럿이 임의 디자인 코드를 안전하게 실행할 수 있다는 뜻은 아니다.
디자인 미리보기에서 합성 fixture를 쓰는 것은 허용된다. 실제 구현의 인수 검사에서는 프론트·백엔드·격리 DB를 연결해야 하며 전부 mock으로 대체한 결과를 최종 통합 증거로 사용하지 않는다.

## 스튜디오에서의 검토·수정

직원은 후보 A/B/C와 해당 기준 버전을 고르고 PC·태블릿·모바일 및 화면 상태를 확인한다. 후보 수나 기기별 검증 완료 표시는 실제 등록·실행 결과에서 나온다. 처음부터 모든 후보가 세 기기에서 검증되었다고 표시하지 않는다.

1. 원문과 REQ에 연결된 화면·동선·권한 상태를 확인한다. 화면·기능·기기별 확인되지 않은 항목을 남긴다.
2. 자연어 수정 요청에 대상 후보와 화면을 연결한다. 예를 들어 메뉴 단순화·사진 크기 조정은 변경할 화면과 상태를 함께 기록한다.
3. 기존 후보를 덮어쓰지 않고 새 revision을 생성한다. 공급자·입력 계약·실행 Attempt와 실패도 보존한다.
4. 변경 전후를 같은 viewport·상태에서 비교한다. 시각 차이와 함께 추가·삭제한 화면, 요구사항·API·자산 변경을 보여 준다.
5. 수정 요청·다른 안·선택 승인 중 다음 행동을 정한다. 선택 승인에는 후보 digest·기준 계약·확인 범위·결정자·사유를 기록한다.

메뉴를 바꾸는 요청이 신규 회원가입이나 개인정보 수집처럼 업무 범위를 바꾸면 Business Contract의 변경 요청으로 돌린다. 디자인 승인만으로 기능·권한·데이터 보존 정책을 추가하지 않는다.
부분 화면만 승인했다면 승인 범위 밖 화면이 통과한 것으로 보이지 않게 한다. 필수 화면·차단 상태가 남으면 전체 Design Contract를 확정하지 않는다.

## 변경과 승인 무효화

후보 상태는 후속 런타임에서 제안·미리보기 준비·검토 대기·수정 요청·선택·거절·STALE을 구분한다. 실행 성공, 디자인 선택, 세 계약의 정합성 통과, 실제 납품 승인은 서로 다른 사건이다.
디자인의 코드·자산·화면 명세·API·REQ 또는 검사 기준이 바뀌면 새 manifest에 이전 승인이나 화면 검증을 붙이지 않는다. 이전 기록은 이력으로 남기되 현재 후보에 대한 효력은 없다. 변경 영향이 확인되지 않으면 미확인으로 보류한다.

`contract_review`에서 확인할 핵심은 다음과 같다.

- 승인한 Business Contract가 요청하는 필수 화면·업무 흐름을 Design Contract가 포함하는가.
- 화면의 입력·표시·오류·권한 상태가 System Contract의 API·필드·타입·업무 정책과 맞는가.
- 내부 추가 제안과 확인된 제외를 고객의 필수 요구사항과 구분했는가.
- 세 계약·후보·미리보기·검토 기록이 같은 현재 revision을 가리키는가.
- 필수 검사·차단 질문·미분류 원문·차단 리뷰가 해결되었는가.

자동 정합성 검사는 정의된 규칙과 연결을 확인한다. 의미상 고객 의도를 모두 충족했다는 증명이나 사람의 디자인 선택을 대신하지 않는다. 디자인 선택 뒤에도 구현·권한·실패 상태·E2E·화면·고객 인수 검사가 남는다.

## 사람 개입과 측정

개입할 때 단계, 원인, 상황, 결정, 결과를 프로젝트·SRC·작업·후보 revision에 연결한다. 고객 정보 부족, 요구사항 모순, 모델 오류, 표준 밖 요청, 접근 권한, 품질 문제를 구분하고 아직 결과가 없으면 미확정으로 둔다. 수정 뒤 재발과 검수 결과도 연결한다.
보존 기간 동안 원문·후보·결정·개입 이력을 덮어쓰지 않고 새 기록을 추가한다. 정정은 새 버전과 이유를 남긴다. 이것이 영구 보존을 뜻하지는 않으며 권한 있는 보존 만료·삭제 정책을 별도로 집행한다. 현재 로컬 파일럿에는 이 삭제·만료 처리와 회원 신원 인증이 없다.

진행률 `82%`나 Coverage `100%`는 정의된 분모·측정 대상·기준 버전·수집 시점이 있을 때만 표시한다. 연결 수, 검사 실행 수, 통과 수, 고객 확인 범위를 구분한다. 숫자가 높다는 이유로 승인하지 않으며 데이터가 없으면 null/미확인으로 표시한다. 합성 데모 수치에는 합성 자료임을 표시한다.

## 후속 구현의 완료 증거

후보 공통 저장 모델과 adapter를 먼저 연결하고, 한 개 합성 사이트로 후보 생성·격리 미리보기·자연어 수정·diff·선택을 재현한다. 이어 실제 인증된 revision 결합과 세 계약 Gate를 서버 경계에서 검증한다.
이전 후보 승인 재사용, 새 디자인의 누락 화면, 계약 밖 API 필드, 악성 가져오기 코드의 운영 접근, Provider 장애·구독 한도, 작업 중 재시작을 각각 검사한다. 격리 경계와 승인 결합이 확인되기 전에는 일반 고객 코드 실행이나 자동 프론트 반영을 완료 기능으로 공개하지 않는다.
현재 저장소에서 확인한 PhotoShift 하네스는 저장소별 오케스트레이션·검증 도구 묶음이다. 별도의 Foundry나 이미 완성된 Task/Attempt/Provider 엔진을 이 스튜디오의 실행 기반으로 가정하지 않는다.
